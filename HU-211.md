## Descripción general

**ContentMS** es un componente Microservicio desplegado en **Code Engine**, con exposición **REST/Json**, que se encarga de:

- Exponer el **POST** para guardar los archivos de contenido estático en el COS de CMS.
- Exponer el **GET** para la consulta de la URL del archivo migrado.

## Recurso `GET /v1/content-loaded`

Capacidad GET con exposición REST/Json para consultar el archivo migrado basado en el texto que viene luego del slash (`/`) del dominio. Debe realizar las siguientes acciones:

1. Consulta el archivo en el Cache de **"Components"** de Redis Cache.
2. Si el archivo no existe en el Cache, entonces lo debe consultar en el COS CMS `/partnerId/Object`, y copia el archivo consultado en el COS al Cache de Redis **"Components"**.
3. Retorna el archivo consultado como binario.

> **Contrato vigente (ver "Desviaciones" al final de esta sección).** El GET se implementó como
> una descarga sin cabeceras: `context_url` es su única entrada y ya identifica al socio.

### Parámetros de entrada

| Nombre | Descripción | Tipo | Obligatoriedad |
|---|---|---|---|
| context_url (in query) | URL de contexto con el socio delante: `<partnerId>/<archivo>`, ejemplo `12345/image1.png` | string | Requerido |

Este recurso **no recibe cabeceras**: `correlation_id`, `request_id` y `_p` no se envían. Si llegan, se ignoran.

### Parámetros de salida (Response 200)

**Header `{in header}`**

Este recurso **no devuelve** `correlation_id`, `request_id` ni `_p`. Las únicas cabeceras de la respuesta son `returnCode`, `message`, `Content-Type`, `Content-Length` y `Content-Disposition`.

**Body `{responseHeader}`**

| Nombre | Descripción | Tipo | Obligatoriedad |
|---|---|---|---|
| returnCode | Código Respuesta "200" | string | Requerido |
| message | Mensaje Respuesta "OK" | string | Requerido |

**Bodyresponse**

| Nombre | Descripción | Tipo | Obligatoriedad |
|---|---|---|---|
| File | File como binario | file | Requerido |

### Parámetros de salida (Response 400, 401, 500)

Mismos bodies `errorHeader` / `errorDetail` que en `POST /v1/save-content`, pero **sin las cabeceras** `correlation_id`, `request_id` y `_p`, que este recurso no lleva en ninguna dirección.

Casos de error propios del `context_url`, todos 400 con `errorDetail.code = INVALID_OBJECT_PATH`:

| Caso | Ejemplo |
|---|---|
| Sin el prefijo del socio | `context_url=image1.png` |
| Con el prefijo vacío | `context_url=/12345/image1.png` |
| Intento de salirse del espacio del socio | `context_url=../99999/image1.png` |
| Lo mismo, ya dentro de la ruta | `context_url=12345/../99999/image1.png` |

Si la clave no existe bajo ese prefijo, 404 con `CONTENT_NOT_FOUND`.

### Desviaciones respecto a la especificación original

Lo que las capturas tabulan para este recurso, y que **ya no aplica**:

| La especificación pedía | Qué se implementó | Por qué |
|---|---|---|
| `correlation_id`, `request_id` y `_p` obligatorios en la petición | Ninguna cabecera | Decisión de producto: simplificar el GET a una descarga directa |
| Devolver esas tres cabeceras en la respuesta 200 | No se devuelven | Consecuencia de lo anterior |
| `context_url` con sólo el nombre, ejemplo `image1.png` | `context_url` = `<partnerId>/<archivo>` | Al no venir `_p`, el socio tiene que viajar dentro del propio `context_url` para poder componer la clave `/partnerId/Object` |

Dos consecuencias que conviene validar con quien escribió la HU:

1. **El GET deja de aislar a un socio de otro.** El `_p` era lo que separaba a los socios en un bucket compartido; ahora el `partnerId` lo pone quien llama, así que quien conozca un id ajeno puede leer sus archivos. Se mantiene la guarda contra `../`, que impide salirse del espacio de socios, pero el aislamiento real tendría que venir de la capa de autorización (el 401 de este contrato sigue sin emisor).
2. **Las líneas de log del GET salen sin correlación**, porque no hay `correlation_id` que propagar al MDC.

El `POST /v1/save-content` **no cambia**: mantiene las tres cabeceras obligatorias tal como las pide la especificación.

## Modelo de datos

Los siguientes son los modelos de datos en MongoDB Service en IBM Cloud FS.

### Redis Cache Service

En el servicio Cloud de Redis Cache se va a almacenar la información de los archivos de contenido estático cargados en la migración desde **Liferay**.

**Collection `Components`**

| Nombre | Descripción | Tipo |
|---|---|---|
| partnerId | Id socio | string |
| fileURLCIS | URL archivo CIS | string |
| filePathCOS | Ubicación física COS | string |
| fileSize | Tamaño del archivo | string |
| fileName | Nombre del archivo | string |
| bucketName | Nombre del bucket | string |
| file | Archivo binario | file |

### MongoDB Service IBM Cloud FS

En el servicio Cloud de MongoDB se va a almacenar la información de la data de los archivos cargados en la migración de contenido estático a Cloud.

**Collection `OutPutsUrls` (temporal para la migración)**

| Nombre | Descripción | Tipo |
|---|---|---|
| fileName | Nombre del archivo migrado | string |
| documentURLCIS | URL documento CIS | string |
| documentType | Tipo documento almacenado, certificado - condicionado - términos... | string |
| documentLoadedDate | Fecha carga documento | date |
| recordNumber | Número del registro en el lote | Integer |
| batchNumber | Número de lote | Integer |

### COS CMS

Estructura de directorios que va a contener el único bucket para el COS de CMS. En este COS se van a almacenar archivos de contenido estático:

```
partnerId
  --> Object
```
